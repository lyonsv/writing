# 0013. Sync: manifest CAS on private Blob, three-way engine in core, guarded desktop client

- **Status:** Accepted
- **Date:** 2026-11-02
- **Related:** ADR 0006 (save pipeline), 0008 (library), 0010–0012 (auth, tokens, storage).

## Context
M5 syncs the library folder between devices through the M4 server. Prose must never be lost or silently overwritten. Devices are often offline, and two of them may edit the same document. Storage is the private Vercel Blob store (per-object ETags and conditional writes, no transactions, no custom metadata). Vercel Functions cap request and response bodies at 4.5 MB. The engine must run on iOS too (M6).

## Decision

### Server storage
- **Manifest:** one object, `sync/manifest.json`, is the source of truth:
  ```json
  {
    "v": 1,
    "seq": 0,
    "entries": {
      "<path>": { "rev": 0, "hash": "<sha256>", "size": 0, "updatedAt": 0, "deleted": true }
    }
  }
  ```
  `deleted` is present only on tombstones.
- **Every mutation is one compare-and-swap of the manifest:** Blob `put` with `ifMatch` on the ETag that was read. On contention it re-reads, re-checks the request's precondition, and retries.
  - That makes create-only, If-Match updates, deletes (tombstones) and **moves** atomic. A move tombstones `from` and creates `to` in the same write.
  - `rev` comes from the manifest-wide counter `seq`, so revs are never reused, even when a path is deleted and re-created.
- **Bodies** are immutable, content-addressed objects at `sync/objects/<sha256>`, written **before** the manifest references them, so a reader never sees an entry without its body.
- **Deviation from the roadmap wording** ("one object per document, folders as path prefixes"): we key bodies by content hash and keep paths in the manifest.
  - Arbitrary user file names (Unicode, `#`, `?`, `%`, spaces) never become Blob pathnames. Their encoding behaviour couldn't be verified locally.
  - Renames are atomic with no copy.
  - Identical content is stored once.
  - The cost: the store isn't browsable by folder. An M8 backup/export reads the manifest and writes `path → object`.
- **Garbage:** objects no entry references (left by a lost race or an overwritten version) accumulate. Collecting objects older than a day that no live or tombstoned entry references is an M8 maintenance task. Until then, old versions also act as an accidental history.
- **Tombstones** are pruned after 90 days. Clients treat "absent" exactly like "deleted", so pruning is safe.
- **Key space:** `sync/` (auth uses `auth/`). Document paths never become keys.

### HTTP API
All routes sit behind the M4 gate, with explicit body limits.

| Route | Purpose |
|---|---|
| `GET /api/sync/manifest` | `{ seq, entries: [{ path, rev, hash, size, updatedAt, deleted? }] }`. `ETag: "m<seq>"`, and `If-None-Match` → 304. |
| `GET /api/sync/file?path=` | The bytes as `application/octet-stream`, with `ETag: "<rev>"` and `X-Margin-Entry` (URL-encoded JSON entry). 404 if absent or deleted. |
| `PUT /api/sync/file?path=` | Body = bytes. **Requires** `If-Match: "<rev>"` or `If-None-Match: *`, else 428 (no blind overwrites). |
| `DELETE /api/sync/file?path=` | `If-Match` required → tombstone. |
| `POST /api/sync/move` | `{ from, to, ifMatch }` → atomic move. `to` must not be live. |

**Errors:**

| Status | Meaning |
|---|---|
| 412 `{ current }` | Precondition failed |
| 409 `{ path }` | Name collides with a live path case-insensitively (macOS and iOS disks are case-insensitive) or as file vs folder (`a.md` vs `a.md/x.md`) |
| 413 | Document over 4 MiB, or the manifest would exceed 4 MiB (its GET must stay under Vercel's response limit) |
| 400 | Invalid path |

- **Path rules** are the same as core's `isSyncablePath`:
  - canonical `normalizeDocPath` form;
  - a `.md` file, with no hidden segments, backslash, NUL or control characters;
  - **Unicode NFC**;
  - every name ≤ 255 UTF-8 bytes and the whole path ≤ 1024 bytes.

  The server has its own copy (`syncPaths.ts`, because it takes only types from core), and a test compares the two on more than 5,000 generated paths.
- **Content is bytes.** Hashes are lowercase hex SHA-256 of the exact bytes on every platform, so BOMs, CRLF and non-UTF-8 files sync byte-exact.
- **Large documents:** documents over **4 MiB are refused with 413** and stay local. The client reports "N document(s) not synced". We did not build client-direct Blob uploads with scoped tokens: that is a second upload path, with its own auth and token-scoping surface, for prose files that are almost never this big. Revisit if it ever matters.

### Engine (`packages/core/src/sync.ts`, pure)
`planSync(local, base, remote)` makes a three-way decision per path. *base* is what this device and the server last agreed on, as `hash` + `rev`.

| Local vs base | Remote vs base | Action |
|---|---|---|
| same | same | nothing |
| same | changed | download (only if local still has the base hash) |
| same | deleted | delete locally (only if local still has the base hash; desktop: to the Trash) |
| changed | same | upload `If-Match: base.rev` |
| deleted | same | delete remotely `If-Match: base.rev` |
| changed | changed | same content → adopt; else **conflict**: write ours to `name (conflict YYYY-MM-DD HHMM).md`, then let theirs take the path |
| changed | deleted | re-create remotely (`If-None-Match: *`): **edit beats delete** |
| deleted | changed | download into the empty path: **edit beats delete** |
| deleted | deleted | forget |
| new (no base) | new | same content → adopt, else conflict |
| new | absent | upload create-only |
| absent | new | download create-only |

- **Renames:** a planned "delete A" plus "create B" whose hash equals A's base hash becomes a single **move**: remote `POST /move`, or a local rename. The file keeps its identity, so an open document follows its rename (ADR 0008's rebase).
- `runSync` executes and re-plans until settled (at most 4 passes). Each local action is **guarded at the moment it acts** by the file's current hash (`write(path, bytes, expect)`, `remove(path, expect)`, `move(…, expect)`), and each remote action by CAS. A lost race is *deferred* and re-planned, never forced.
- The base is saved after every action, so a crash mid-run loses no knowledge.
- A lost or empty base is safe: with no base nothing is ever deleted, and differing content becomes conflict copies.
- **Tests:** every row of the table; races inside the executor; and 300 seeded simulations of two devices with random edits, deletes and renames, the user typing mid-sync, and the other device syncing mid-run. Each asserts convergence (both devices equal the server) and **no data loss**: any text a user produced survives unless a user replaced or deleted it on a device where it was present. `SYNC_SEEDS=3000` passes. Mutants that drop the conflict copy or the local guard fail.

### Desktop client (`apps/desktop/src/sync.ts`, main process)
- **When it runs:** while signed in, on start and sign-in, every 30 s, about 3 s after any library change (watcher), after switching folders, and on Margin › **Sync Now** (⌥⌘S). One run at a time; a request during a run queues exactly one more.
- **Before each run** every renderer flushes through the ADR 0006 handshake, so uploads include what was typed. A renderer that doesn't answer within 3 s makes the run skip, and is never destroyed (unlike quit).
- **Downloads** go through `FileSystemLibrary.writeForSync`: the per-path queue, a hash check, then temp + fsync + rename. They deliberately **don't** update the open document's known version. The watcher then reports the change like any external edit: a clean editor reloads, and a dirty editor's next save goes to a conflict copy (ADR 0006). Tested with an open document and stale editor text.
- **Deletes** use `removeForSync` → `shell.trashItem`, and only if the file still matches the base.
- **Base and hash cache** live in `userData/sync/<sha256(serverUrl, login, libraryRoot)>.json`. That is per server, per account and per library folder: switching any of them starts from an empty (safe) base. The hash cache (size + mtime → hash) avoids re-reading unchanged files; a refused guarded write drops the entry.
- **Paths:** local names are mapped to NFC for sync and written back under NFC names (APFS is normalisation-insensitive). Files that aren't syncable (non-`.md`, hidden, too long) are ignored.
- **Status** (`SyncStatus`: `off | idle | syncing | offline | error` + message) goes to the renderer. A quiet line bottom-left reads "Synced", "Syncing…", "Offline" or "Sync error"; it is hidden in focus mode and while signed out. Offline or signed out, the library works exactly as before.

## Consequences
- One manifest object means every write rewrites it, and writes from all devices serialise on its ETag. That's fine for one person, but it caps the library at roughly 20k documents (4 MiB of manifest) and makes each write O(library size).
- **Conflict copies** use the minute-resolution name, plus a counter. Two devices conflicting on the same path in the same minute create differently-numbered or nested copies; everything is kept.
- **Case-only differences** between a local file and an independently created remote file (`a.md` here, `A.md` there, no base) are refused by the server (409) and retried each run without data loss. The user resolves it by renaming. Same for the rare file-vs-folder collision.
- The 30-second timer polls the manifest (one Blob read, or 304) even when idle.
- **Not verified on real Vercel Blob** (local only by brief): whether Blob's `ifMatch` on `put` gives the compare-and-swap semantics assumed here, and its latency with `useCache: false`. Check on first deploy (ROADMAP M8).

## Amendments (2026-11-02, verified against the real private Blob store)
- On real Blob, `SyncRepository` passes the following (`verify:blob`):
  - 10 concurrent If-Match updates of one document → one wins, nine get 412;
  - 10 concurrent creates of different documents all land;
  - 10 writers racing to create the manifest itself all land.

  That needed the ADR 0012 amendment fixes (weak ETags; state-based classification of conditional failures; previously a concurrent first creation of the manifest returned 500).
- The manifest CAS loop retries with capped exponential backoff plus jitter for up to ~25 s, instead of 20 quick attempts. A real round trip is ~300 ms, and N concurrent writers need up to N rounds.
- **Stale reads and rollbacks (validator M5, MAJOR 1).** A rev mismatch used to count as "remote changed", so a manifest *older* than the base (lagging replica, or a server restored from backup) could trash files created since, or download older text over newer. The planner now gets the manifest's `seq` and marks a path **stale** (no action, reported as a sync error) when:
  - the server reports a lower rev than the base for it (live or tombstone);
  - it is missing entirely (not even a tombstone) from a manifest whose `seq` isn't above the highest base rev. A real delete bumps `seq`, and tombstones are only pruned by later writes.

  A whole manifest with `seq` below the highest base rev is a rollback: every base path is stale and nothing runs, not even uploads. Downloads also refuse a body whose rev is below the base. Tests: planner cases, a restored-backup run that changes nothing locally, a desktop integration rollback, and 300 seeded simulations serving stale manifests 30% of the time. These assert that sync never removes a file the server still has, and never overwrites with a non-current version, at the moment it acts. With the guards removed, 305 tests fail. Recovering from a real rollback is manual for now: the status says so, and the files stay put.
- **Hash cache key (validator M5, MAJOR 2).** The cache was keyed on size + mtime, so a same-size edit with mtime preserved (`cp -p`, `rsync -t`) never uploaded, and the status said "Synced". Combined with a remote delete, it was retried forever under a misleading "case" message. The key is now size + mtime + **ctime + inode** (ctime can't be set by users). **Any** refused or failed local action (write, remove, move, conflict copy) drops that path's cache entry, as does a read whose hash disagrees with the cache. The deferred-items message now just says they will be retried. Desktop integration tests cover both scenarios with exactly preserved mtimes, and fail on the old code.
- **Case folding (validator M5, MINOR 5).** Collisions were checked with `toLowerCase()`, which accepts both `ß.md` and `SS.md`, but they are one file on APFS. `foldPathCase` in core (NFC → upper → lower → NFC) folds `ß`/`ss`, `ſ`/`s`, digraphs (`ǅ`/`Ǆ`) and ligatures (`ﬀ`/`ff`), and treats composed and decomposed accents alike. The server's copy (`syncPaths.ts`) is checked against core on a corpus of tricky characters. The server uses it for 409 collisions; the desktop skips a second local file that folds to an already-listed one (possible only on case-sensitive volumes). This is still an approximation of APFS's own case-folding table, but it's stricter than before.
